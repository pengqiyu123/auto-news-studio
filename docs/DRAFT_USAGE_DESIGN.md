# Auto News Studio 第二阶段设计文档：稿件使用逻辑

更新时间：2026-04-28

## 概述

本文档是 [INFO_COMPOSITION_COMPARISON.md](./INFO_COMPOSITION_COMPARISON.md) 的姊妹篇。INFO_COMPOSITION 回答的是"有什么工具可用"，本文档回答的是"用户怎么用、何时用、谁决定"。

核心原则：**AI 生成，人来决定**。AI 的角色是提效工具，不是决策主体。

## 1. 触发机制：自动 vs 手动

### 现状

当前系统有三种触发方式：

| 触发方式 | 代码位置 | 说明 |
|---------|---------|------|
| `radar_and_draft` 自动 | `store.py:2942` | 每轮自动从 watchlist 生成最多 N 篇 |
| `full_pipeline` 自动 | `store.py:2942` | 同上，还顺延分发 |
| 手动"生成稿件"按钮 | `store.py:3367` | 用户点一次生成一篇 |
| 批量"构建摘要"任务 | `store.py:3388` | 批量从候选池生成多篇 |

### 设计问题

当前的问题是：**自动生成不看质量阈值**。`radar_and_draft` 模式只要事件进入 watchlist 就生成，不检查事件是否够热、是否适合写成文章。

### 设计决策

**双轨触发机制**：

```
轨道 A：自动触发（radar_and_draft / full_pipeline 模式）
  └── 条件：事件进入 watchlist AND alert_state ∈ {rising, breakout}
  └── 可选约束：composite_score >= 阈值（用户可配置，默认不设）

轨道 B：手动触发
  └── 从热点簇页面：用户点"生成稿件"按钮
  └── 从预警台页面：用户点某个 alert 对应的"生成稿件"
  └── 从稿件台：用户点"批量生成"从候选队列拉 N 篇
```

**理由**：参考 AIWriteX 的事件驱动触发 + md2wechat 的手动单篇控制，两种都要。自动轨道保证不会漏掉突发热点，手动轨道保证用户有最终选择权。

## 2. 来源选择：哪些事件变成稿件

### 现状

当前生成逻辑 (`store.py:1843-1854`) 只从 `watchlisted=true` 的事件生成稿件。但用户无法配置哪些事件值得写入。

### 设计问题

- 哪些事件值得写？没有量化标准
- 同一事件多轮触发时，是否重复生成？
- 事件和稿件的对应关系：1:1？1:N？

### 设计决策

**事件 → 稿件映射规则**：

```
1. 同一事件只生成一次初稿（按 event_id 去重）
2. 已发布的稿件对应事件仍可更新（生成"新版本"而非"新稿件"）
3. 稿件必须关联到 1 个或多个 IntelEvent（多事件合并写稿场景）
```

**事件准入评分**（可配置）：

| 条件 | 权重 | 说明 |
|------|------|------|
| alert_state = breakout | +40 | 爆发级别优先 |
| alert_state = rising | +25 | 上升级别次优 |
| platform_count >= 3 | +20 | 跨平台热度高 |
| source_count >= 5 | +15 | 信源充分 |
| member_count >= 5 | +10 | 素材量大 |
| member_count = 1 | -20 | 单条素材不值得写 |

**理由**：参考 TrendRadar 的"相关性评分 + 用户兴趣过滤"模式。这不是强制规则，而是给用户一个参考指标，哪些事件"值得写"。

## 3. 人类介入节点：编辑 → 预览 → 审核 → 发布

### 现状

当前稿件流程已有这些节点，但分散在不同位置：

```
事件 watchlist
  → compose_draft() 生成稿件
  → DraftEditorModal 编辑（TipTap + 实时预览）
  → "通过"按钮 = 审核
  → "草稿箱"按钮 = 推微信草稿
  → "预览"按钮 = 打开预览页
  → "推进发布"按钮 = 执行 Playwright 发布链
```

### 设计决策

**四段式审核流程**：

```
阶段 1：生成 (Generated)
  AI 完成初稿生成
  状态：drafted / preview_ready
  用户看到：标题 + 摘要 + 正文预览
  可用操作：编辑 / 重生成 / 丢弃

阶段 2：编辑 (Editing)
  用户在 TipTap 编辑器中修改
  状态不变（仍为 drafted）
  实时预览 WeChat HTML 渲染效果
  可用操作：去 AI 味 / 重新生成（带上用户编辑作为上下文）

阶段 3：审核 (Review)
  用户点击"保存并推送草稿"
  状态：preview_ready → approved（需显式通过）
  推送至微信草稿箱
  用户需登录微信后台确认

阶段 4：发布 (Published)
  微信后台手动发布，或启用自动发布
  状态：approved → published
  可选：同步至其他平台（Wechatsync）
```

**每个阶段必须有明确的状态标签和可用操作**，不能出现"发布按钮可以点击但实际无法发布"的状态。

## 4. 编辑器设计

### 现状

当前 `DraftEditorModal` 已有：
- TipTap 富文本编辑器
- Markdown 源码切换
- 实时保存（自动保存）
- 实时预览（WeChat HTML）

### 设计决策

**左侧编辑 + 右侧预览的分栏布局**（当前已是）：

| 区域 | 功能 | 状态 |
|------|------|------|
| 标题编辑 | 可修改标题、备选标题 | 已实现 |
| 正文编辑 | TipTap 富文本 | 已实现 |
| 元数据侧边栏 | 来源数、时间上下文、风险词 | 待增强 |
| 预览面板 | WeChat HTML 渲染 | 已实现 |
| 操作栏 | 重生成 / 去 AI 味 / 保存 | 部分实现 |

**新增功能**：

1. **去 AI 味按钮**：在编辑阶段提供一键去 AI 味
   - 位置：编辑器工具栏右侧
   - 显示处理强度选项（温和 / 中等 / 激进）
   - 处理后高亮显示修改的段落
   - **在保存前执行**，不影响用户编辑内容

2. **编辑上下文重生成**：
   - 用户可点击"重新生成"并选择是否带入当前编辑内容
   - 避免"重生成会丢失所有编辑"的问题
   - 参考 md2wechat 的 `preview` 模式

3. **版本历史**：
   - 每次重生成保存一个版本
   - 用户可在下拉菜单中切换历史版本
   - 可对比两个版本的差异

## 5. 发布流程

### 现状

当前发布流程 (`publishers.py`)：
- 推草稿箱：`_sync_shadow_wechat_draft`
- 打开预览：`open_preview`
- 浏览器发布：`publish_draft`（Playwright 自动化）

### 设计决策

**两阶段发布：草稿 → 正式发布**

```
微信草稿箱阶段（半自动）：
  1. 编辑完成 → "保存到草稿箱"
  2. 系统推 HTML 到微信草稿队列
  3. 用户在微信后台手动确认/修改 → 正式发布
  4. 记录发布状态回传给系统

发布后同步阶段（可选）：
  1. 用户在系统内勾选"同步到其他平台"
  2. 调用 Wechatsync MCP 推送到知乎/掘金等
  3. 各平台分别显示同步状态
```

**理由**：md2wechat 和 Wechatsync 都采用"草稿优先"策略——默认不自动发布，必须用户手动确认。这是对公众号运营者负责的做法。

**自动发布选项**（可配置）：
- 关闭（默认）：只推草稿，用户手动发布
- 开启：确认后自动点击发布按钮（仍有 Playwright 兜底）

## 6. 错误处理

### 当前状态

当前稿件流程中的错误处理：
- LLM 失败：模板兜底 (`compose_draft` 有 fallback)
- 微信 API 失败：`last_error` 字段记录，显示阻断原因
- 图片缺失：`blocked_reasons` 字段记录

### 设计决策

**分级错误展示**：

| 错误级别 | 表现 | 处理方式 |
|---------|------|---------|
| 阻断性 | 红色 badge + 阻断原因文案 | 必须修复才能继续 |
| 警告性 | 黄色 badge + 警告文案 | 可继续但需注意 |
| 信息性 | 灰色文案 | 不影响流程 |

**具体错误场景处理**：

```
场景 1：LLM 生成失败
  → 使用 Python 模板兜底
  → 状态：drafted（与 LLM 生成一样）
  → 显示："使用模板生成，内容可能较简略"
  → 允许用户手动完善

场景 2：微信 API 推送失败
  → 重试 2 次（指数退避）
  → 仍失败则记录 last_error
  → 状态：preview_ready（不阻塞审核）
  → 提供"重试推送"按钮

场景 3：编辑保存失败
  → 自动保存失败时弹窗提示
  → 提供"导出 Markdown"按钮作为保底
  → 用户可重新打开文件继续编辑

场景 4：Token 过期
  → 检测到 401 响应
  → 弹窗："微信授权已过期，请在设置中重新授权"
  → 跳转设置页面

场景 5：内容超长
  → 微信限制单篇图文不超过 20000 字
  → 超出时提示并提供"拆分为多篇"选项
```

## 7. 多稿件管理

### 现状

当前 `DraftTable` 支持：
- 搜索（标题/摘要/封面建议）
- 按阶段筛选（drafted/preview_ready/approved/published/failed）
- 按审核状态筛选
- 按更新时间/来源数/标题排序

### 设计决策

**稿件队列视图**：

```
┌─────────────────────────────────────────────────────────────┐
│ 稿件工作台                                                   │
├─────────────────────────────────────────────────────────────┤
│ 全部(24) │ 待编辑(5) │ 待审核(8) │ 待发布(3) │ 已发布(8)   │
├─────────────────────────────────────────────────────────────┤
│ [搜索...]  [阶段▼]  [审核▼]  [排序▼]     [批量操作▼]       │
├─────────────────────────────────────────────────────────────┤
│ □ 标题1  │ drafted    │ pending │ 今天 10:30  │ 编辑...  │
│ □ 标题2  │ preview... │ pending │ 今天 09:15  │ 预览...  │
│ □ 标题3  │ approved   │ approved│ 昨天 18:00  │ 发布...  │
└─────────────────────────────────────────────────────────────┘
```

**批量操作**：
- 批量"生成稿件"：从候选队列拉 N 篇
- 批量"推送草稿箱"：将多篇同时推微信
- 批量"重新生成"：对多篇重新调用 LLM
- 批量"同步平台"：对多篇调用 Wechatsync

**稿件 → 事件追溯**：
- 每篇稿件显示来源事件（如"来源：3 个热点事件"）
- 点击可跳转到热点簇页面查看源事件详情

## 8. 去 AI 味时机

### 关键决策点

去 AI 味应该在流程的哪个节点执行？

### 设计决策

**在编辑阶段执行，作为"润色"选项**：

```
稿件生成 → [用户编辑内容] → [可选：去 AI 味] → 预览 → 保存
```

具体实现：

```
时机：用户在编辑器内点击"去 AI 味"按钮
处理：
  1. 对当前 markdown 内容调用 humanizer
  2. 高亮显示被修改的句子（diff 展示）
  3. 用户可选择：
     - 接受修改 → 内容替换
     - 拒绝修改 → 保留原文
     - 调整强度 → 温和/中等/激进
  4. 记录本次 humanize 强度到稿件元数据
```

**理由**：参考 md2wechat 的三种强度设计 + AIWriteX 的五维质量评分。去 AI 味放在编辑阶段是因为：
1. 用户已经看过了内容，知道哪些地方 AI 痕迹重
2. 去味后的内容仍可编辑，不会被强制替换
3. 作为可选步骤，不会增加默认流程的复杂度

**AI 味评分**（可选显示）：
- 引用 AIHumanize.io 或 md2wechat 的评分逻辑
- 在编辑器右上角显示"AI 味评分：72/100"
- 低于 60 分建议去味，高于 80 分可接受

## 9. 多平台同步策略

### 现状

当前只支持微信公众号（Playwright 自动化），Wechatsync 未集成。

### 设计决策

**三平台同步策略**：

```
同步时机：用户主动触发，不自动同步
同步对象：已发布或已审核通过的稿件
同步方式：Wechatsync MCP Server
```

**同步流程**：

```
1. 稿件发布/审核通过后，工具栏显示"同步到其他平台"按钮
2. 点击打开同步面板：
   ┌─────────────────────────────────┐
   │ 同步到其他平台                    │
   ├─────────────────────────────────┤
   │ ☑ 知乎（需登录）                  │
   │ ☑ 掘金（需登录）                  │
   │ ☐ CSDN（需登录）                 │
   │ ☐ 小红书（需登录）                │
   │ ☐ 头条号（需登录）                │
   └─────────────────────────────────┘
   [取消]  [开始同步]
3. 显示同步进度和结果
4. 各平台同步状态分别记录
```

**平台优先级**：
1. 知乎（技术类内容首选）
2. 掘金（开发者社区）
3. CSDN（存档价值高）
4. 头条号（流量大）
5. 小红书（年轻用户群）

**注意事项**：
- 各平台内容格式不同，需做平台适配（标题/摘要/标签）
- 部分平台需额外授权（如知乎 OAuth）
- Wechatsync MCP Server 集成工作量较大，列为 P2

## 设计原则总结

| 原则 | 说明 |
|------|------|
| **AI 生成，人来拍板** | AI 负责提效，重大决策（发布/同步）必须人来确认 |
| **草稿优先** | 默认只推草稿，不自动发布 |
| **可追溯** | 每篇稿件必须能追溯到源事件，发布后能追溯到发布状态 |
| **渐进复杂** | 简单场景（手动单篇生成）零门槛，高级功能（批量/同步）按需开启 |
| **错误有出口** | 每个失败场景都有可操作的后续步骤，不是卡死 |
