# Projects 写作能力调研

更新时间：2026-05-26

## 方向修正

本文件保留第一轮调研时的项目拆解，但其中对 `auto-news-分发版-v2.4.1` 的产品价值评价偏高。

修正后的判断是：`auto-news-分发版-v2.4.1` 的全手动人机协同流程不适合作为 `Auto News Studio` 的下一阶段方向。它只能作为局部 prompt 纪律、事实约束字段和反面流程样本参考。

新的主方案见同目录下的 `AUTO_EDITORIAL_DESK_PLAN_20260526.md`，应以后者作为后续优化方向基准。

## 目标

本轮调研不是泛泛看 `projects/`，而是为了回答一个更具体的问题：

`Auto News Studio` 要怎样提升“公众号文章创作能力”，尤其是以下三类能力：

1. 新闻事实约束
2. 文章结构与写作策略
3. 微信公众号成稿与排版适配

本结论基于 `D:\python\Auto-news2\projects` 中与内容创作高度相关的项目进行筛选和拆解。

## 一轮筛选结论

`projects/` 下并不是每个项目都值得深挖。

本轮最有价值的项目分成 4 类：

1. `wechat-writer`
   价值：通用写作 scaffold、模板资产化、交互式需求补齐
   局限：不是完整成稿引擎，也没有新闻事实约束

2. `auto-news-分发版-v2.4.1`
   价值：最接近当前主项目的旧形态，已经形成“事实抽取 -> 角度选择 -> 正文生成 -> 标题优化”的写作链
   局限：整体仍偏单篇流水线，写作深度和素材包能力有限

3. `AIWriteX-main`
   价值：模板驱动、风格驱动、视觉驱动很强，适合借鉴“排版层”和“风格层”
   局限：野心很大，但新闻事实纪律相对弱，容易滑向“爆文机器”

4. `md2wechat-skill`
   价值：对“风格写作”“AI 去痕”“微信排版工具链”有很强的方法化沉淀
   局限：更像写作/排版工具，不是新闻生产系统

补充价值项目：

5. `ai_news_rss_summarizer-main`
   价值：提供“长资讯 -> 分类摘要 -> executive summary”的压缩思路
   局限：更像日报分析器，不是公众号成稿链

6. `DataCube-AI-Space-main`
   价值：提供“抓取 -> 分类 -> 处理 -> 翻译 -> 存储”的多阶段资讯流水线视角
   局限：偏资讯站与报告，不直接解决公众号文章写作表达

低优先级项目：

1. `wechat-publisher-mcp`
   更偏发布接口封装，不提升写作质量本身。

2. `Wechatsync`
   更偏多平台分发，不提升文章创作能力本身。

## 重点项目拆解

## 1. wechat-writer

### 它真正是什么

`wechat-writer` 本质上是一个 Skill 型内容脚手架，不是生产级文章引擎。

它的仓库组织很清楚：

1. `SKILL.md` 负责流程说明
2. `templates/` 提供文章类型模板
3. `references/` 提供写作经验
4. `scripts/` 提供演示级脚本

但真正的生成脚本 `scripts/02-generate-content.js` 只是模拟流程和进度条，输出里明确保留：

- `[AI 将在此处生成公众号文章内容]`

这说明它没有把真实 LLM 成稿能力封装在仓库中。

### 它的可借鉴点

1. 文章类型层做得清楚
   `templates/公众号文章模板.md` 把公众号文章拆成：
   - 深度分析型
   - 教程实操型
   - 案例拆解型
   - 观点评论型
   - 清单整理型
   - 故事叙述型
   - 对比评测型

   这很适合拿来作为 `Auto News Studio` 的“文章形态选择层”。

2. 交互式补信息思路明确
   `SKILL.md` 里把交互拆成：
   - 前 3 轮锁定骨架：内容类型、目标受众、核心目的
   - 后 4-7 轮填充血肉：场景、关键信息、语气、参考案例

   这值得迁移到当前 Agent 写作链里，尤其适合“用户手动补观点”的场景。

3. 模板资产化表达直观
   它把“标题公式”“段落结构”“结尾 CTA”写成显性资产，而不是埋在代码里。

### 它不适合直接照搬的点

1. 没有新闻事实边界
   它面向通用内容创作，不是新闻型写作，缺少“只允许使用已验证素材”的硬约束。

2. 模板过泛
   模板适合通用内容，但不够适配“今天发生了什么，为什么值得写”这种新闻任务。

3. 没有素材包概念
   它直接从主题走向文章，没有“事实包 / 引文包 / 时间线包 / 风险点包”。

### 结论

`wechat-writer` 最适合借鉴的是：

1. 文章类型层
2. 交互补全层
3. 模板资产化表达方式

不适合把它当成完整写作后端。

## 2. auto-news-分发版-v2.4.1

### 它为什么重要

这是 `Auto News Studio` 最值得继承的近亲项目，因为它已经形成了一个很清晰的人机协同写作链。

在 `src/wechat_news/processors/collab_processor.py` 中，核心流程是：

1. Step 1：事实抽取
2. Step 2：角度选择
3. Step 3：正文生成
4. Step 4：标题优化

这比单次“让模型直接写一篇文章”成熟得多。

### 它最值得借鉴的地方

#### 1. 先事实，后观点

Step 1 的 prompt 先提取：

1. `core_facts`
2. `who_is_affected`
3. `what_changed`
4. `potential_risks`
5. `news_value_score`

这个拆法很对，因为它把“新闻是什么”先压成结构化中间层，再进入写作。

#### 2. 角度不是随便起，而是围绕“读者决策问题”

Step 2 的提示词里有一个非常强的约束：

- 每个角度必须回答一个普通消费者的决策问题

而且明确区分了：

- 正确：买不买、等不等、选哪个
- 错误：行业策略是否成功、供应链压力多大

这是很强的产品意识。它不是让 AI 随便“找角度”，而是逼它回答“读者为什么现在必须看这篇文章”。

#### 3. 正文生成里明确了事实纪律

Step 3 的 prompt 有一条非常关键的规则：

- 以上是你唯一可以使用的事实来源。任何不在上述列表中的数据、时间、价格、参数都是编造，必须用模糊表述替代。

并且详细规定了：

1. 价格没给就不能写价格
2. 时间没给就不能编时间
3. 配置没提就不能补参数
4. 对比没提就不能补百分比

这套纪律非常适合并入当前 `Auto News Studio` 的写作链。

#### 4. 冷启动规则很强

Step 3 还定义了前 150 字必须出现：

1. 决策问题
2. 利益点
3. 冲突点

这非常适合公众号首屏阅读逻辑，能直接提升开头抓力。

#### 5. 简讯和长文分开设计

在 `prompts.py` 里：

1. `VIRAL_BRIEF_PROMPT` 强调“只基于原文事实”的 200-300 字简讯
2. `VIRAL_HIGHLIGHT_PROMPT_BASE` 强调“背景 + 科普 + 行业影响 + 用户影响 + 观点”的 800-1200 字重点文章

这说明它已经意识到：

- 简讯不是短版长文
- 长文不是扩写简讯

这是当前主项目很值得继承的内容层分工。

### 它的不足

1. 读者模型偏窄
   它把很多角度都压向“普通消费者决策”，这适合消费科技，但不一定适合基础设施、政策、安全事件。

2. 写作风格偏“爆文驱动”
   prompt 明显追求情绪冲突、利益点和点击动机，适合拉开读者注意力，但容易过猛。

3. 素材利用还不够细
   虽然有事实抽取，但还没有真正形成当前主项目更需要的：
   - 时间线
   - 引文
   - 多来源证据包
   - 正文全文摘录优先级

### 结论

`auto-news-分发版-v2.4.1` 是本轮最值得继承的方法来源。

最值得吸收的不是它的 UI，而是它的写作流程纪律：

1. 事实中间层
2. 角度选择层
3. 正文生成中的硬事实约束
4. 标题与导语后置优化

## 3. AIWriteX-main

### 它的强项不在“新闻真相”，而在“爆文表现层”

`AIWriteX` 是一个非常激进的内容生产系统。它强调：

1. 热点选题
2. 多智能体协作
3. AI 自动配图
4. 微信模板化排版
5. 去 AI 味
6. 风格与创意变体

从当前目标看，它最有价值的不是“新闻写作纪律”，而是后两层：

1. 风格表现层
2. 模板排版层

### 它最值得借鉴的地方

#### 1. 模板适配要求写得很细

在 `src/ai_write_x/core/unified_workflow.py` 中，模板填充要求非常具体：

1. 保持 `section` 结构和内联样式不变
2. 保持视觉层次、色彩方案和布局风格
3. 标题替标题、段落替段落、列表替列表
4. 内容变长变短时允许局部调整，但不破坏布局
5. 不可使用模板中的任何日期作为新文章日期

这说明它已经把“内容生成”和“视觉适配”拆成两层，这是很成熟的思路。

#### 2. 微信排版作为独立任务层

它没有把“排版”混进正文生成里，而是单独设模板工作流和设计工作流。

这很值得 `Auto News Studio` 继续坚持：

- 文本质量和视觉质量应该分层处理

#### 3. 风格与创意维度化

它支持：

1. 文体风格
2. 语言风格
3. 创意维度组合
4. 参考文章借鉴比例

这对当前主项目的启发是：

- 我们也应该显式引入“文章风格配置”，而不是只靠单个 prompt 隐式控制语气。

### 它的问题

1. 容易偏离新闻事实
   它整体目标更像“爆文工厂”，不是“新闻事实优先工作台”。

2. 视觉优先级过高
   对当前主项目来说，排版当然重要，但不能压过事实与论证。

3. 过多功能会稀释主线
   小说、手机智能体、热点预测、创意变换等都很酷，但不应该直接迁移进当前主项目。

### 结论

`AIWriteX` 最值得借鉴的是：

1. 内容层与模板层分离
2. 模板填充规则写清楚
3. 风格配置显式化

不建议照搬它的“爆文驱动叙事”和超重功能堆叠。

## 4. md2wechat-skill

### 它的价值不在新闻写作本身，而在“写后处理”

`md2wechat` 更像一个公众号内容工具链，强项有三个：

1. Markdown -> 微信 HTML
2. writer style
3. humanize 去 AI 味

### 它最值得借鉴的地方

#### 1. 把“写作风格”做成配置资产

`writers/dan-koe.yaml` 展示了一套很成熟的 writer-style 资产结构：

1. `core_beliefs`
2. `writing_style`
3. `paragraph_rules`
4. `formatting`
5. `punctuation_rhythm`
6. `writing_prompt`
7. `title_formulas`
8. `quote_templates`
9. `cover_prompt`

这非常值得借鉴，因为它把“风格”从一句笼统描述，升级成了一个可编辑、可扩展、可复用的配置对象。

#### 2. 把“观点 -> 成文”作为独立流程

`write` 命令的逻辑不是拿一篇完整文章排版，而是从：

- idea
- fragment
- outline

这类不完整输入出发，生成结构化写作请求。

这说明它非常适合做：

- 观点补全
- 表达重写
- 风格迁移

#### 3. AI 去痕不是一句空话，而是独立能力

它明确把 `humanize` 单列为能力，并且强调：

1. 去公式化表达
2. 打破均匀结构
3. 注入真实观点
4. 保留原意

这对当前主项目很有价值，因为公众号长文常见问题不是“没有信息”，而是“有信息但太像 AI 写的”。

### 它的局限

1. 它不负责新闻事实纪律
2. 它的 writer style 当前更偏个人表达，不是新闻评论
3. 它更像写作工具链，而不是选题生产系统

### 结论

`md2wechat` 很适合为 `Auto News Studio` 提供两类能力：

1. 风格资产层
2. 去 AI 味后处理层

## 5. ai_news_rss_summarizer-main

### 价值

这个项目的价值很单纯：

1. 把复杂长资讯切块
2. 先做 chunk analysis
3. 再做 executive summary
4. 输出清晰 HTML 报告

它说明“先分段压缩，再汇总结论”是处理长资讯很有效的方式。

### 对主项目的启发

当前 `Auto News Studio` 在做 deep dive 或简报时，也可以借鉴这个两层压缩：

1. 先对来源做分块摘要
2. 再基于块级摘要生成总括判断

这样比直接把所有正文全文一把喂给模型更稳。

## 6. DataCube-AI-Space-main

### 价值

它最重要的启发是“资讯处理流水线分段化”：

1. Fetch
2. Classify
3. Process
4. Translate
5. Save

并且 `Process` 阶段已经显式包含：

1. summary 生成
2. entity 提取
3. 多栏目内容分流

### 对主项目的启发

对 `Auto News Studio` 来说，它最大的借鉴价值不是文风，而是：

1. 处理链拆阶段
2. 各阶段输出有明确中间产物
3. 资讯站与内容站之间的桥梁是“结构化内容对象”

## 综合判断（已修正）

第一轮调研的项目拆解仍有价值，但结论顺序已经被后续讨论和补充调研修正。

如果目标是“公众号短讯 MVP”，参考价值排序应改为：

1. 当前 `auto-news-studio`
   现有事件、deep dive、brief、微信草稿同步是主干。

2. `TrendRadar-master`
   借鉴热点筛选、兴趣方向、新增热点、展示与分析解耦。

3. `newshub-main`
   借鉴批处理、去重、摘要/关键词/检索信号；不借鉴静默失败。

4. `auto-news-分发版-v2.4.1`
   只借鉴事实纪律与短讯/长文分层，不借鉴全手动产品形态。

5. `wiseflow-master`
   借鉴发布边界、自媒体运营流程和浏览器自动化等待纪律。

6. `md2wechat-skill`
   后续长文阶段借鉴风格资产与去 AI 味。

7. `AIWriteX-main`
   后续借鉴模板/排版分层，不借鉴爆文默认气质。

8. `wechat-writer`
   后续长文升级阶段借鉴文章类型和交互补信息。

9. `DataCube-AI-Space-main`
   借鉴资讯流水线分段化，但离公众号短讯较远。

补充调研见 `TRENDRADAR_NEWSHUB_WISEFLOW_SUPPLEMENT_20260526.md`。

## 面向 Auto News Studio 的借鉴建议（已压缩）

当前阶段不应该把写作链正式拆成 5 层，也不应该先做角度矩阵、文章类型配置、writer-style 或去 AI 味。

第一阶段只做“今日短讯”：

1. 从现有 `intel_events` 和 `event_deep_dives` 选 Top 3-5。
2. 复用现有 `BriefItem` 生成 300-600 字短讯。
3. 显示事实、风险、来源、微信草稿状态。
4. 一键同步微信草稿箱。
5. 失败必须显式暴露，不能用空摘要或兜底文案伪装成功。

后续再把第一轮调研中的能力逐步恢复为升级项：

1. 长文升级时再引入文章类型。
2. 重大事件再做角度规划。
3. 长文稳定后再做 writer-style。
4. 排版层保持独立，不和正文生成混写。

## 不建议做的事

1. 不建议直接引入 `AIWriteX` 式的“爆文化过强”写作语气作为默认方案
2. 不建议把 `wechat-writer` 的通用模板直接当新闻写作模板
3. 不建议把去 AI 味做成会篡改事实和数字的全文重写
4. 不建议为了视觉效果牺牲微信稳定性

## 下一步实施建议（已修正）

最合理的推进顺序是：

1. 新增 `build_daily_brief_candidates(limit=5)`，只做候选筛选和短讯投影。
2. 新增 `GET /api/admin/editorial/daily-briefs`，返回今日短讯候选。
3. 前端在总览页新增“今日短讯”卡片区。
4. 复用现有 `POST /api/admin/briefs/{brief_id}/wechat-draft` 同步草稿。

暂时不要实现：

1. 重型 `EditorialPackage`
2. 角度规划层
3. 多文章类型模板
4. writer-style
5. 去 AI 味
