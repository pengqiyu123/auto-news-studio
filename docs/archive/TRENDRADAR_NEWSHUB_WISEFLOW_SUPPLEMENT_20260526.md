# TrendRadar / newshub / wiseflow 补充调研

更新时间：2026-05-26

## 背景

第一轮 `projects/` 调研遗漏了几个与新闻发现、自媒体运营更相关的项目：

1. `TrendRadar-master`
2. `newshub-main`
3. `wiseflow-master`
4. `RSSHub-master`
5. `n8n-master`

其中前三个对当前“公众号短讯 MVP”最有直接参考价值。本文件只记录可落地结论。

## 1. TrendRadar-master

### 判断

这是最接近 `Auto News Studio` 产品方向的参考项目，但本地副本不是适合直接复用的业务后端。

它的核心价值是产品机制：

1. 多平台热点聚合
2. 关键词/兴趣筛选
3. 时间段调度
4. 新增热点提示
5. AI 分析与推送展示解耦
6. 多渠道推送

### 对 Auto News Studio 的启发

`Auto News Studio` 的“今日短讯”不应该只是已有 brief 列表，而应该是：

```text
按用户关注方向和事件热度筛出来的今日可发清单。
```

可借鉴：

1. 用户关注方向配置，先用现有 watchlist/tags，不急着做自然语言兴趣文件。
2. 新增热点优先，避免旧事件反复占位。
3. 推送内容短，后台分析可长。
4. 每组最多展示几条，避免一个热点霸屏。

不建议第一阶段借鉴：

1. MCP 服务
2. 多渠道推送
3. 复杂 timeline 配置
4. AI 翻译
5. 全量热点报告 UI

## 2. newshub-main

### 判断

`newshub` 更像新闻聚合与个性化检索系统。它的后端有真实新闻处理链：

```text
fetch news
-> batch process
-> dedupe
-> summarize/analyze
-> generate embedding
-> store/search
```

### 可借鉴点

1. 批处理：每批处理少量文章，降低模型/API 失败风险。
2. 去重：用标题归一化减少重复内容。
3. 结构化摘要：摘要、情感、关键词可作为筛选信号。
4. 向量检索：后续可用于“找相似来源”和“补背景”。
5. 个性化偏好：后续可做用户关注方向，不必第一阶段上。

### 明确不借鉴

`geminiService.js` 在摘要失败时会返回：

```text
summary: ""
sentiment: "neutral"
keywords: []
```

然后处理链继续存储。这对新闻生产是危险的，因为它把失败伪装成了一个可用结果。

本项目必须相反：

```text
模型失败 -> 标记失败/证据不足 -> 不生成可同步短讯
```

## 3. wiseflow-master

### 判断

`wiseflow` 的新闻写作价值不如 `TrendRadar/newshub`，但它对“自媒体运营边界”和“发布自动化纪律”很有价值。

`selfmedia-operator` 里明确区分：

1. 素材积累
2. 选题研究
3. 图文输出
4. 发布策略
5. 外部平台发布需要用户确认

### 可借鉴点

1. L3 发布动作必须由用户明确授权。
2. 中间素材与最终稿件分开管理。
3. 浏览器自动化发布时必须等待平台解析完成。
4. 发布前要检查封面、标签、AI 辅助声明等平台要求。

### 对当前阶段的意义

短讯 MVP 只进入微信草稿箱，不做自动正式发布。

原因：

1. 草稿箱是低风险闭环。
2. 正式发布涉及账号声誉、平台规则和合规声明。
3. 当前最需要验证的是“短讯选题与成稿质量”，不是发布机器人。

## 修正后的参考排序

面向“公众号短讯 MVP”，参考价值排序应为：

1. 当前 `auto-news-studio`
   现有事件、deep dive、brief、微信草稿同步是主干。

2. `TrendRadar-master`
   借鉴热点筛选、兴趣方向、时间段/新增热点、展示与分析解耦。

3. `newshub-main`
   借鉴批处理、去重、摘要/关键词/检索信号；不借鉴静默失败。

4. `auto-news-分发版-v2.4.1`
   只借鉴事实纪律与短讯/长文分层，不借鉴全手动产品形态。

5. `wiseflow-master`
   借鉴发布边界、自媒体运营流程、浏览器自动化等待纪律。

6. `md2wechat-skill`
   后续长文阶段借鉴风格资产与去 AI 味。

7. `AIWriteX-main`
   后续借鉴模板/排版分层，不借鉴爆文默认气质。

8. `wechat-writer`
   后续长文升级阶段借鉴文章类型和交互补信息。

9. `DataCube-AI-Space-main`
   借鉴资讯流水线分段化，但离公众号短讯较远。

## 对下一步实现的影响

第一阶段不是做“完整选题台”，而是做“今日短讯”：

```text
事件池/深挖结果
-> 今日候选 Top 3-5
-> 生成短讯
-> 同步微信草稿箱
```

核心设计要求：

1. 使用现有 `BriefItem`，不要新建重型 `EditorialPackage`。
2. 候选是投影对象，不是文章生命周期对象。
3. 失败必须暴露，不能用空摘要、样例内容、兜底伪成功。
4. 正式发布仍需用户确认。
